## 1.5 SDK Upgrade

### Result: Pin upgraded from `1.15.1` → `1.22.0`

### Why not `1.29.0`?

Bisected version-by-version. `1.23.0` introduced **Zod v4 dual-support** (PR [#1040](https://github.com/modelcontextprotocol/typescript-sdk/pull/1040)) — `registerTool` accepts both Zod v3 and v4 schemas via conditional types. With our 80 tool registrations, the resulting type inference recursion exceeds TypeScript's stack budget:

```
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
sh: line 1: 66664 Abort trap: 6           tsc
```

Even with `NODE_OPTIONS=--max-old-space-size=8192`, the build aborts with native stack overflow after ~110s. Bisection:

| Version | Build | Notes |
|---|---|---|
| 1.15.1 | ✅ (1s) | original pin |
| 1.20.0 | ✅ (1s) | clean |
| 1.22.0 | ✅ (1s) | **chosen ceiling** |
| 1.23.0 | ❌ OOM | Zod v3/v4 dual-support introduced |
| 1.25.0 | ❌ OOM | same root cause |
| 1.29.0 | ❌ OOM | same root cause |

### Why `1.22.0` is a good landing spot

Notable improvements between 1.15.1 → 1.22.0:

- **PR #816**: `registerTool` accepts `ZodType<object>` for input/output schema (more flexible)
- **SEP-986**: Specified format for tool names (validation we should adopt — see §3 for naming compliance)
- **SEP-1319**: Decoupled request payloads, removed passthrough iteration, typecheck fixes
- **SEP-1034 + 1330**: Default values for elicitation schemas (relevant when we add resources/prompts later)
- **SEP-991**: URL-based client metadata registration

### Future path to 1.23+ (out of Phase 1.5 scope)

Two tracks:

1. **Migrate to Zod v4** in our project (Zod v3.25 is the floor for the dual-support; v4 is the forward path). Removes the need for the conditional type union.
2. **Annotate tool registrations explicitly** to short-circuit type inference at each `registerTool` call site (e.g., `server.registerTool<typeof MySchema>(...)`).

Either approach unlocks the 1.23+ feature surface (URL elicitation, sampling-with-tools, SEP-1577 form-mode, etc.). Tracked as a follow-up after Phase 6.

### Verification (Phase 1.5 done)

- `npm run build` clean in 1s
- `node dist/index.js` starts, completes handshake, accepts SIGTERM
- All 80 tools register without error
- DB migrations apply (already at 1.7.0; nothing pending)

## 5. Pre-handshake Startup Work (`src/index.ts`)

Currently runs synchronously before `server.connect(transport)`:

| Step | File ref | Cost | Move? |
|---|---|---|---|
| `dotenv.config()` | line 26 | < 5 ms | stay |
| `new McpServer({name, version})` | line 28–31 | < 1 ms | stay |
| `new DatabaseService()` | line 33 | **5 ms – 2 s+** (runs migrations + base schema) | flag — see Phase 3 |
| `new FileExportService(db)` | line 34 | < 5 ms | stay |
| `new ResultsService(db, fileExport)` | line 35 | < 5 ms | stay (starts cleanup timer, fine) |
| Compute worker script URL | lines 39–42 | < 1 ms | stay |
| `new WorkerPool({ workerScript })` | line 42 | **~50–200 ms** (spawns N worker threads) | possibly defer to post-handshake |
| `new ImapService(db)` + `setWorkerPool` | lines 44–45 | < 5 ms | stay |
| `new SmtpService()` | line 46 | < 5 ms | stay |
| `registerTools(server, ...)` | line 49 | ~10–30 ms (80 schema registrations) | stay |

Detached (already correctly post-handshake-ish):

- `fileExport.sweepOrphans(...)` (line 52) — async, doesn't block.

`server.connect(transport)` is awaited inside `main()`. The orphan sweep runs concurrently with the handshake, which is correct.

**Phase 3 candidates to defer or measure:**
1. **DatabaseService migrations** — could be moved post-handshake if no tool needs them up-front. (Risk: tools that hit the DB on first call would fail. Need migration to be idempotent + finished before any tool fires.)
2. **WorkerPool thread spawn** — main thread blocks while threads spawn. Defer to lazy first-use.

The existing path is likely under 2s on warm starts (DB at v1.7.0, no migrations to apply), but a fresh install on a cold platform could exceed it.

## 6. Capability Negotiation Status (covers #80)

`McpServer` is constructed with only `{name, version}`:

```typescript
const server = new McpServer({
  name: 'imap-mcp-pro',
  version: '2.13.1',
});
```

The SDK auto-derives `tools` capability from `registerTool()` calls. We do **not** explicitly declare:

- `resources` (we serve none, so this is correct)
- `prompts` (none)
- Any experimental capabilities

**Phase 3 work (closes #80):** Pass an explicit `capabilities` object to `McpServer` for clarity and to opt out of any auto-detection ambiguity. Format per SDK 1.22:

```typescript
const server = new McpServer({
  name: 'imap-mcp-pro',
  version: '2.13.1',
  capabilities: {
    tools: { listChanged: false },  // we don't support listChanged notifications
    // resources: explicitly omit — we serve none
    // prompts: explicitly omit — we serve none
  },
});
```

This makes our supported surface unambiguous to clients and stops the SDK from advertising features we don't implement.
